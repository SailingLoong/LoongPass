# Desktop account activation and Codex Windows support

## Implementation

The Windows native owner supplies the existing Flutter account page with saved official identities and read-only snapshots. The official Store package is discovered at runtime. The desktop application is selected by its adjacent official CLI capability; extension-host and command-runner registrations are not desktop candidates.

Official configuration, browser authorization and renewal use an owned stdio app-server child. Credentials remain native. The child is stopped and reaped before reading its final grant. Cancellation, EOF, timeout and normal shutdown clean up owned work and private temporary homes. The macOS authorization/renewal paths now also read the final grant after child shutdown.

Activation asks for closure confirmation, preserves the outgoing account's latest grant, refuses unrelated command-line writers, observes the selected desktop tree's exit, revalidates the package and effective policy, and applies authentication with audited local preferences in a journaled transaction. Successful activation opens Codex, including when it was previously stopped. A failed action restores a desktop that it interrupted. Windows discloses forced termination; macOS requests application exit and preserves Codex's own force-quit/cancellation dialog.

Saved credentials and newly staged files use private user/SYSTEM permissions. Existing official files can retain Codex's read-only sandbox access; foreign write access, reparse points, hard-linked credentials, unexpected file changes and unrecognized recovery states are refused. Configuration, conversation databases, MCP and skills are outside the write API. Cloud caches, capabilities and queued actions are not transferred to the target identity.

The C++ code is necessary Windows SDK integration within the existing Flutter application. The UI continues to use Forui and the existing font/theme contract. Shared synthetic fixtures check parity with the macOS identity and preference projection.

Both native adapters recognize the earlier renderer snapshot and the installed macOS client's newer content-owner JSON format. In the latter, already-shared local state remains shared; only the audited local atoms and twelve local owner-scoped preference values seed the target. The active content-owner marker is left for the official client to transition. Unknown owners, ambiguous formats and an existing `.codex-global-state.sqlite` settings store stop activation before authentication changes; SQLite preferences are not implemented. This settings database is separate from conversation databases, which remain untouched.

## Closure confirmation for all supported switches

The November 17 clarification makes this a shared product rule: confirm closure, wait for the client to exit, apply the selected account, then open the client, including when it was initially stopped. Cancellation or unconfirmed exit stops before account application. Current user-facing desktop switches are Codex on macOS/Windows and WorkBuddy on macOS. Other providers do not currently expose a desktop switch; this follow-up does not add those missing implementations or activate the dormant ZCode bridge.

WorkBuddy already has the required native exit → guarded session write → open sequence. Its account-row and details actions now both show a Forui confirmation first, identify the selected account, explain possible task interruption, and state that the client opens after account application. Confirmation is separate from operation progress. Cancel, owner replacement or disposal during confirmation cannot invoke activation. The native grant owner, desktop write transaction and exit/open implementation are unchanged.

### Official login notification compatibility

Investigation found a Windows protocol error independent of the older transport/storage checks. The installed official Windows CLI `0.167.0-alpha.3.2` generates an `AccountLoginCompletedNotification` schema where `loginId` may be absent or null and only `success` is required. Windows incorrectly required a string ID, so a valid unscoped completion could interrupt an unrelated `account/read` after renewal. The macOS bridge already ignores such completions.

A controlled native child reproduced rejection against the unchanged qualified Windows library. The fix ignores absent/null IDs, retains validation of malformed IDs/success fields, and correlates named browser logins as before. Complete Windows native checks passed after recompiling the affected runtime; the new macOS parity check also passed, with no macOS production change. A focused independent review found no actionable findings. The original failed desktop request's raw RPC frames were not retained, so its precise historical frame is not asserted.

A fresh source-matched Windows package and complete real A → B → A remain required after this fix. Installer acceptance is also pending; the earlier real run used the qualified portable package. The original macOS two-account round trip and new WorkBuddy prompt's Mac visual acceptance remain unverified; the local Mac hosts active Codex work. The macOS-only build [43935823139](https://github.com/SailingLoong/LoongPass/actions/runs/43935823139) passed Universal compilation and packaging, and its complete archive matched the Actions SHA-256 after an incomplete connector download was discarded. No running-client Mac acceptance is inferred from that package.

Private logs and account evidence remain outside Git under the task's artifact directory. The user authorized transferring two existing Mac grants to the Windows acceptance machine over SSH; grant portability and actual online identities must be established by the official client.
